## 1. Problem and non-goal

The canonical row already has an authoritative `Message.id` and `(conversation_id, index_in_session)`. The missing fact is the exact relationship between a pre-persistence optimistic row and the later canonical user row. A client cannot predict `index_in_session`: history may be unresolved and assistant/tool-originated messages or another tab may advance the sequence.

The fix adds one correlation value spanning optimistic creation, POST, canonical persistence, and history GET. It does **not** replace canonical identity, carry model context, gate sending on frontend history, or create a new retry/idempotency subsystem.

## 2. Frozen wire and persistence contract

### 2.1 Request

`POST /api/agents/chat/<conversation_id>/` accepts an additive body field:

- wire name: `client_turn_id`;
- value when present: canonical UUID string generated by the V4 Desktop immediately before an ordinary send attempt;
- absent remains accepted for V3, non-V4 callers, existing tests, and other producers;
- present-but-empty, non-string, or invalid UUID returns HTTP 400 before conversation preference, Message, runtime reservation, upload-finalization, or generation side effects;
- `client_turn_id` is valid only for an ordinary send that creates a new user Message. A request with `edit_message_id` plus `client_turn_id` returns HTTP 400.

Both SSE and async modes use the same POST body and persistence rule. No SSE event, polling event, response header, or async ACK field is added in this closure.

### 2.2 Canonical Message

Add one field to `memory.models.Message`:

- model name: `client_turn_id`;
- type: nullable UUID;
- database uniqueness for non-null values;
- old rows are migrated as `NULL`; no data backfill;
- non-user roles must keep it `NULL` (enforce in the model/database contract, not merely by frontend convention).

For an ordinary send with a valid request UUID, the exact canonical user Message created for that send stores the UUID in the same creation path. This applies to:

1. direct/provider ordinary chat, including text and attachment/audio-anchor user rows;
2. managed/subscription-runtime ordinary chat where the canonical user Message is created inside the atomic runtime-binding seam.

Other Message producers remain `NULL`, including assistant/system/developer rows, historical rows, tools such as assistant `send_message`, bridge/group paths not entered through this ordinary Chat POST, and edit/regenerate operations that do not create the ordinary optimistic user row.

A duplicate non-null UUID must never bind a second Message. This contract does not require replaying or returning the first operation as an idempotent success; an explicit conflict/error is acceptable. Existing runtime no-duplicate-POST and uncertainty handling remains authoritative.

### 2.3 History response

`memory.serializers.MessageSerializer` exposes additive read-only field:

```text
client_turn_id: string | null
```

The field is present in both paginated and legacy full-array `GET /api/agents/chat/<conversation_id>/` message rows because both use the same serializer. UUIDs serialize canonically; rows without a binding return `null`.

## 6. Scope exclusions / razor

Explicitly excluded:

- blocking send because frontend history is pending or failed;
- predicting the next `index_in_session`;
- matching by content, timestamp, attachments, latest-row position, or async token;
- adding SSE `user_ack`, polling events, response headers, or arrival types;
- changing how backend conversation context is assembled for the model;
- introducing general POST idempotency, retry replay, or a new runtime lifecycle state;
- backfilling UUIDs for existing messages;
- changing edit/regenerate/branch semantics.

These exclusions are deliberate: the single persisted correlation round-trip is sufficient to close the approved UI identity defect without coupling send availability to UI cache state.
